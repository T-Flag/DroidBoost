## Q1. Which apps are the reference tools in 2025–2026, and what is each one's profile (developer, price, open source, access needed, maintenance, free vs Pro)?

### Takeaway
DevCheck (flar2) is the most-cited all-round reference. It is free with no ads, Pro is sold as a subscription or a lifetime purchase, and Shizuku or root unlock extra data. Around it sit three groups of apps. The first is spec/info apps: CPU-Z (ads), AIDA64, CPU Info (open source), Device Info HW, Device Info (ytheekshana) and Inware (v7 in April 2026). The second is Shizuku-based overlay / FPS tools: Scene, FrameX, FPS Meter, GameBench FPS Monitor. The third is root-only kernel managers, which are mostly declining: Kernel Adiutor has been archived since 2019 and SmartPack was archived in July 2026, while EX Kernel Manager and Franco Kernel Manager are still paid apps. Google's own tools are diagnostics, tracing and developer options, not live dashboards.

#### Shizuku (the enabler most non-root monitoring apps depend on)
- Lets normal apps call system APIs with **ADB (shell) or root privileges** through a Java process started with `app_process`, relaying calls to system_server over binder. ADB permissions "are limited and vary by Android version". Apache-2.0 — [GitHub README, official](https://github.com/RikkaApps/Shizuku)
- **v13.6.0 (25 May; year not shown on the releases page, probably 2025):** "Support Android16 QPR1", and **auto-start without root on Android 13+ when connected to a trusted WLAN** — [GitHub releases, official](https://github.com/RikkaApps/Shizuku/releases)
- **Android 17 breakage:** issue #2180 (opened 17 June 2026) reports that Shizuku 13.6.0 shows 0 authorized apps on Android 17 on Pixels, **including the Pixel 8 Pro**. Forks (Shizuku+, Nightzuku, Shevery, thedjchi/Shizuku) work. A commit titled "Merge fix: authorized apps list empty on Android 17" dated 22 October 2026 references the issue, which was still open at the time of reading — [GitHub issue #2180](https://github.com/RikkaApps/Shizuku/issues/2180)

### Inferences
- DevCheck is the main benchmark for "what is covered". It sits in the same niche as our planned app (free info, plus overlays, widgets, battery monitoring and Shizuku/root extras). Its Pro paywall (overlays, widgets, battery monitoring, tests, Benchmark Labs) shows which features users treat as "premium".
- Inware is the closest "modern Pixel-styled" competitor and has started exposing thermal throttling status and cycle count (2026). Its users are asking for widgets, which is a gap we could fill.
- The ecosystem is moving from root to Shizuku. Root kernel managers are disappearing (SmartPack archived in July 2026, Kernel Adiutor in 2019), while new Shizuku-based open-source overlays are appearing (FrameX, FPS Meter, Thermal Monitor). Most of them are Snapdragon-centric, and none explicitly lists Tensor support.
- Depending on Shizuku is a real risk on Android 17: the official build broke for months on Pixels. Our app should handle the Shizuku service being missing or unauthorized gracefully, and possibly support forks.

## Q2. Feature coverage: what do existing apps cover, who covers it, and at what access level?

### Takeaway
Without root or Shizuku, apps reliably cover static specs (SoC, cores, display, camera, sensors list and live sensor values, storage, network), per-core CPU **frequency**, RAM totals, battery temperature/voltage/current, thermal **status/headroom** (through Android APIs) and overlays/widgets. **CPU load, per-app memory, detailed thermal zones, battery health and real FPS** usually need Shizuku/ADB. Root is needed for **GPU frequency/governor control, voltages and DDR frequency**.

## Q3. What is broken or limited on Android 14/15/16/17 without root, and what do Shizuku/ADB or root unlock?

### Takeaway
The main hard limits are SELinux and framework restrictions. `/proc/stat` has been blocked since Android 8, so there is no true CPU load for untrusted apps. Other apps' processes have been invisible since Android 5/7. `HardwarePropertiesManager` is restricted to device owner / VR / `DEVICE_POWER`. Thermal sysfs access is device-dependent. Battery state-of-health fields are system APIs. Official replacements are `PowerManager` thermal status and headroom (API 29/30), CPU/GPU headroom (API 36), and Android 14's public cycle count. Shizuku (ADB shell uid) gives back CPU load, `dumpsys thermalservice`, SurfaceFlinger FPS, battery-stats fields and per-app memory. Root adds GPU frequency, voltages, DDR and tuning.

### Cited Findings
- **CPU load:** since Android 8, `/proc/stat` is labelled `proc_stat` in SELinux and readable only by specific domains (init, shell, system_server), as a fix for side-channel attacks — [AOSP sepolicy commit "restrict access to timing information in /proc"](https://gerrit.omnirom.org/plugins/gitiles/android_system_sepolicy/+/5423db6eb3622183a201eaaa7b39bcbf788eecdb%5E%21); "all of /proc/stat has been disabled for non-System apps", and CPU usage can only be guessed from frequency — [StackOverflow archive, forum](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/46182041/get-cpu-usage-of-a-device-running-android-8-oreo)
- AnotherMonitor documents the effect. On **Android 7.0** an app can no longer see other processes' CPU usage. On **Android 8.0+** neither total CPU usage nor its own process's CPU usage is available, so only memory works. The README claims "rooting doesn't help", which is AnotherMonitor's own claim and contradicts DevCheck, which does show CPU load with root — [AnotherMonitor README](https://github.com/AntonioRedondo/AnotherMonitor); contrast with [DevCheck FAQ](https://devcheck.app/faq)
- **Process lists:** since Android 5.x, `getRunningTasks()` / `getRunningAppProcesses()` are deprecated and return only the caller's own process — [AndroidProcesses library README](https://awesome.ecosyste.ms/projects/github.com%2Fjaredrummler%2Fandroidprocesses); AOSP lockdown of `getRunningAppProcesses` behind `REAL_GET_TASKS` (CVE-2015-3833) — [AOSP commit](https://android.googlesource.com/platform/frameworks/base/+/aaa0fee%5E!/)
- **HardwarePropertiesManager** (API 24: CPU/GPU/battery/skin temperatures, CPU usage, fan speeds) throws a `SecurityException` unless the caller is the **device owner, the bound VR listener service, or holds `DEVICE_POWER`** (a signature permission). Profile-owner support was removed. A normal API-30 app hit the exception in practice — [developer.android.com](https://developer.android.com/reference/android/os/HardwarePropertiesManager); [AOSP source (android-25)](https://chromium.googlesource.com/android_tools/+/HEAD/sdk/sources/android-25/android/os/HardwarePropertiesManager.java); [StackOverflow archive](https://kaweah.freedombox.rocks/kiwix/content/stackoverflow.com_en_all_2023-11/questions/73301124/how-can-i-use-hardwarepropertiesmanager-android-in-android-api-30-android-11)
- **Thermal sysfs:** denials appear as `avc: denied { search }` for `untrusted_app` on the `sysfs_thermal` label. The policy varies by device, and fixes require changing the device's sepolicy — [android-platform Google Group, forum](https://groups.google.com/g/android-platform/c/4sWX7LQhoto); [android-porting group](https://groups.google.com/g/android-porting/c/zz-o7c7FqBM). The Qualcomm reference policy reportedly allows `/sys/class/thermal` for all processes, and when an OEM blocks it, Thermal Monitor falls back to `dumpsys thermalservice` (Thermal HAL) through Shizuku — [Thermal Monitor README](https://github.com/dfdevx2/Thermal-Monitor-Snapdragon)
- **What the Shizuku (ADB) level gives vs root** (documented for Snapdragon by Thermal Monitor): ADB gives CPU frequency through `scaling_cur_freq`, per-cluster load, temperatures on most devices, GPU load and battery data. **ADB lacks GPU frequency, GPU memory, DDR frequency and voltages.** Root adds `cpuinfo_cur_freq` (the actual hardware frequency), GPU frequency and memory, and DDR frequency (with debugfs) — [Thermal Monitor README](https://github.com/dfdevx2/Thermal-Monitor-Snapdragon). In kernel terms, `scaling_cur_freq` is the cached or last-requested frequency, while `cpuinfo_cur_freq` reads the hardware — [LKML](https://lkml.iu.edu/hypermail/linux/kernel/1707.2/03114.html)
- **FPS:** an unprivileged app only sees its own frames (Choreographer). The real game frame rate needs Shizuku/ADB to query SurfaceFlinger (`dumpsys SurfaceFlinger`, `--timestats`) — [FPS Meter README](https://github.com/rdevz-ph/FPS-Meter-Android); [FrameX README](https://github.com/MaheshSharan/FrameX-Android)
- **Official thermal APIs (no permission needed):**
  - `PowerManager.getThermalHeadroom(forecastSeconds)` (API 30; NDK `AThermal_getThermalHeadroom` API 31) returns 0.0 (no throttling) to 1.0 (SEVERE). **Calling it more than once every 10 s can return NaN.** A first value of NaN means the device doesn't support it.
  - `getThermalHeadroomThresholds()` was added in Android 15.
  - Thermal status listeners report NONE…SHUTDOWN. Some devices always return `THERMAL_STATUS_NONE`.
  — [ADPF thermal guide, official](https://developer.android.com/games/optimize/adpf/thermal)
- **Android 16 (API 36):** `SystemHealthManager.getCpuHeadroom()` and `getGpuHeadroom()` (with `CpuHeadroomParams` / `GpuHeadroomParams`) return 0–100 (0 = no more CPU available) or NaN. Each has a minimum polling interval getter (`getCpuHeadroomMinIntervalMillis`), sits behind a feature flag, and throws `UnsupportedOperationException` where unsupported — [SystemHealthManager reference](https://developer.android.com/reference/android/os/health/SystemHealthManager); [Android 16 release blog](https://android-developers.googleblog.com/2025/06/android-16-is-here.html); [AOSP source](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/os/health/SystemHealthManager.java)
- **Battery (Android 14):** `BatteryManager` added cycle count, charging status, manufacturing date, first-use date, charging policy and state of health. **Only cycle count and charging status are public.** The others are system APIs that need an ADB- or Shizuku-granted permission. Accuracy depends on the charging IC and the HAL — [FoneArena (Mishaal Rahman findings)](https://www.fonearena.com/blog/395005/android-14-battery-health.html); [Android Authority](https://www.androidauthority.com/android-14-battery-health-check-3331255/); [androidguias](https://en.androidguias.com/Visible-battery-cycles-in-Android-14-extend-the-life-of-the-mobile/)
- **Shizuku status on recent Android:** official 13.6.0 supports Android 16 QPR1 and can auto-start without root on a trusted Wi-Fi network on Android 13+ — [releases](https://github.com/RikkaApps/Shizuku/releases). It broke on **Android 17** (stable since 16 June 2026) on Pixels including the 8 Pro: the authorized apps list comes up empty. Forks work, and a fix commit was referenced on 22 October 2026 — [issue #2180](https://github.com/RikkaApps/Shizuku/issues/2180); [Droid-Life, Android 17 rollout](https://www.droid-life.com/2026/06/16/android-17-update-pixel-phones-download/)
- **Legacy-era apps** already showed limits on Android 6+: "some features do not work properly with Android 6.0 and up" (Simple System Monitor) — [APKPure](https://apkpure.com/simple-system-monitor/com.dp.sysmonitor.app)

### Inferences
- For our unrooted Pixel 8 Pro app, the realistic baseline (no Shizuku) is:
  - per-core frequency from sysfs: CPU-Z and CPU Info show it with "no special permissions", but this is untested on Tensor / Android 17;
  - `ActivityManager.MemoryInfo` for RAM;
  - `ACTION_BATTERY_CHANGED` / `BatteryManager` for temperature, current, voltage and cycle count;
  - `PowerManager` thermal status and headroom (polled at 10 s or slower);
  - `SystemHealthManager` CPU/GPU headroom (Android 16+), sensors through `SensorManager`, and an overlay through `SYSTEM_ALERT_WINDOW`.
- A Shizuku mode is worth adding for CPU load (`/proc/stat` as shell), `dumpsys thermalservice` (all Thermal HAL temperatures including skin), per-app memory (`dumpsys meminfo`), SurfaceFlinger FPS and battery SoH. It must cope with Shizuku outages such as the Android 17 one.
- `getThermalHeadroom` is rate-limited (10 s), so a "live" thermal headroom graph has to be sampled slowly or combined with status listeners.

### Gaps
- No source confirmed whether untrusted apps on **Pixel 8 Pro / Android 16–17** can read `/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`, `/sys/class/thermal/thermal_zone*/temp` or `/proc/meminfo` (including the SwapTotal/zRAM lines). The next step is to test this on the device.
- Rate limiting of `getRunningAppProcesses` / `getProcessMemoryInfo` in recent AOSP: an AOSP change adding a `RateLimitingCache` was seen in search results, but its release version could not be confirmed.
- No Android 17-specific new restrictions or new monitoring APIs were researched because the search budget ran out.
- Could not fetch perfetto.dev to document power-rail (ODPM) and thermal data sources available through ADB on Pixel.

## Q4. What is specific to the Pixel 8 Pro / Tensor G3 that monitoring apps support or ignore?

### Takeaway
Tensor G3 throttles hard and early: within about a minute on XDA's test, with throttling governed by software "virtual-skin" zones from about 37 °C. Its GPU is a Mali-G715 MP7 (890–940 MHz), while most open-source overlays target Adreno/Snapdragon. The Pixel 8 Pro's infrared thermometer is locked to Google's system app. No app found specifically maps Tensor thermal zones, so this is open ground for a Pixel-specific monitor.

### Cited Findings
- **GPU:** Tensor G3 uses an Arm **Mali-G715 MP7** (7 cores) at about 890 MHz, with a boost of about 890–940 MHz. It is not an Immortalis GPU, as was initially suspected — [Notebookcheck Mali-G715 MP7](https://www.notebookcheck.net/ARM-Mali-G715-MP7-GPU-Benchmarks-and-Specs.762528.0.html); [devicespecifications](https://www.devicespecifications.com/en/model-cpu/60d75dfa); [XDA Pixel 8 Pro performance test](https://www.xda-developers.com/google-pixel-8-pro-performance-evaluation/); [Digital Trends](https://www.digitaltrends.com/phones/google-pixel-8-tensor-g3-chip-good-or-bad-explained/)
- **Throttling behaviour (2023 reviews; test conditions vary):**
  - XDA: the prime core dropped from **3 GHz to 1.9 GHz**, and the performance and efficiency clusters to **1.4 GHz**, within about a minute, once the battery reached **32 °C** — [XDA](https://www.xda-developers.com/google-pixel-8-pro-performance-evaluation/)
  - Beebom: throttled to **60%** of peak in a 15-minute CPU throttling test, with the phone only at about 39 °C — [Beebom](https://beebom.com/google-tensor-g3-benchmarks/)
  - Digital Trends: about **40 °C** after a 20-minute stress test — [Digital Trends](https://www.digitaltrends.com/phones/google-pixel-8-tensor-g3-chip-good-or-bad-explained/)
  - Wccftech: steady loss of performance over repeated 3DMark Wild Life runs — [Wccftech](https://wccftech.com/pixel-8-pro-tensor-g3-geekbench-6-and-3d-mark-wild-life-benchmarks/)
- **Thermal zones:**
  - Tensor SoC temperatures come from the ACPM TMU service, with sensor order **BIG, MID, LITTLE, G3D (GPU), ISP, TPU** (gs101 lineage; Tensor G4 adds AUR). This is from a Linux mainlining PR, so it is an analogue rather than confirmed Pixel 8 Pro names — [GitHub PR](https://github.com/derekross/linux-omarchy-mobile/pull/86)
  - The Pixel 8 Pro uses software-computed **virtual-skin** zones such as `VIRTUAL-SKIN-CPU-LIGHT-ODPM`, `VIRTUAL-SKIN-CPU-MID`, `VIRTUAL-SKIN-CPU-HIGH` and `VIRTUAL-SKIN-SOC` — [XDA guide, updated 14 May 2026, forum](https://xdaforums.com/t/update-14-05-2026-tensor-running-too-hot-fix-overheating-improve-battery-life-on-stock-android-no-custom-rom-no-custom-kernel-pixel-phones.4785321/)
  - The default SOC (CPU+GPU) virtual-skin throttling threshold starts at **37 °C** on the Pixel 8 series — [XDA "Thermal-Throttling-Modifier [Pixel 8 Pro]" mod, forum](https://xdaforums.com/t/mod-thermal-throttling-modifier-pixel-8-pro.4638106/)
- **Infrared thermometer (Thermometer app):**
  - The sensor measures object surface temperature on the Pixel 8 Pro, 9 Pro, 9 Pro XL, 10 Pro and 10 Pro XL — [Pixel Help, official](https://support.google.com/pixelphone/answer/14103759?hl=en)
  - The body-temperature mode is FDA-cleared — [Tom's Guide](https://www.tomsguide.com/phones/android-phones/pixel-8-pro-temperature-sensor-is-fda-cleared-to-measure-your-body-temperature-heres-how-to-do-it)
  - Skin-temperature readings can be stored in the app or in Fitbit — [Notebookcheck](https://www.notebookcheck.net/Google-releases-new-thermometer-features-for-Pixel-8-Pro-Pixel-9-Pro-and-Pixel-9-Pro-XL-in-Europe-with-latest-update.883145.0.html)
  - The sensor is reportedly a Melexis MLX90632 — [Android Central](https://www.androidcentral.com/phones/google-pixel-8-pro-thermometer-test)
  - **Third-party access appears blocked:** the permission `com.google.sensor.permission.FAR_INFRARED_TEMPERATURE` is granted only to system apps (2023 reverse-engineering thread) — [XDA forum](https://xdaforums.com/t/thermometer-reverse-engineering.4635859/)
- **Pixel-only tools that touch monitoring:** Battery diagnostics and network troubleshooting in Settings (launched first on the Pixel 8 series) — [PhoneArena](https://www.phonearena.com/news/you-can-now-troubleshoot-battery-and-network-issues-on-the-google-pixel-8-series-via-a-new-app_id151537); Pixel Diagnostics `*#*#7287#*#*` — [Android Central](https://www.androidcentral.com/apps-software/how-to-run-diagnostics-on-your-pixel)
- **Android version on the target device:** Android 17 stable rolled out on 16 June 2026 and the Pixel 8 Pro is eligible (seven years of updates). Android 17 QPR2 is in beta, with stable expected in December 2026 — [Droid-Life](https://www.droid-life.com/2026/06/16/android-17-update-pixel-phones-download/); [Android Update Tracker](https://www.androidupdatetracker.com/p/google-pixel-8-pro); [Gizmochina](https://www.gizmochina.com/2026/06/17/stable-android-17-rolling-out-to-google-pixels-check-eligible-devices-new-features-and-more/)
- **Open-source overlays and Tensor:**
  - ThermalOverlay's frequency control is Qualcomm-only and Tensor is not mentioned — [GitHub](https://github.com/teldommm/ThermalOverlay)
  - Thermal Monitor is explicitly "for Snapdragon devices" — [GitHub](https://github.com/dfdevx2/Thermal-Monitor-Snapdragon)
  - FPS Meter's temperature path covers "Qualcomm Snapdragon and MediaTek" — [GitHub](https://github.com/rdevz-ph/FPS-Meter-Android)
  - CpuFloat was "extensively tested on Qualcomm" — [XDA](https://xdaforums.com/t/app-cpufloat-march27-floating-cpu-gpu-temperatures-deep-sleep-network-monitor.3204420/)

### Inferences
- Because Pixel throttling is driven by virtual-skin zones at a low threshold (about 37 °C), a Pixel-focused monitor gains more from showing **skin/virtual-skin temperature, `THERMAL_STATUS` and headroom** next to per-cluster frequency (to spot the 3 GHz → 1.9 GHz drop) than from raw per-core temperatures.
- The infrared thermometer is effectively unusable by our app, even sideloaded, unless the device is rooted or the app is installed as a privileged system app.
- The Mali GPU on Tensor is a blind spot. Existing Shizuku tools document GPU load only for Adreno (`gpubusy`), so GPU frequency and load on the Pixel 8 Pro probably need root or a Perfetto/ADB route. This is not verified.

### Gaps
- The exact `thermal_zone*/type` list on a Pixel 8 Pro running Android 16/17, and which zones an untrusted app vs the shell uid can read, were not found in any source. This needs an on-device test (`adb shell cat /sys/class/thermal/thermal_zone*/type`, `dumpsys thermalservice`).
- Whether DevCheck, AIDA64, CPU-Z or Inware show Tensor G3 GPU frequency/load or thermal zones on an unrooted Pixel 8 Pro could not be checked, because Reddit and XDA were inaccessible and the search budget ran out.
- Whether the Pixel 8 Pro exposes Android 14's `BatteryManager` state of health and cycle count, and whether Settings > Battery health appears on the 8 Pro (some reports limit it to newer Pixels), was not verified.
- Pixel ODPM power rails (on-device power monitor, accessible through Perfetto/ADB) were not researched because perfetto.dev was blocked.
